# Synthetic Phase 1 evaluation fixtures

**These files are synthetic development/evaluation fixtures only.** They exist
solely to drive `eval/run_phase1_gate.js` (the executable Phase 1 gate) and
the tests that exercise it. They are never used by, or shipped with, the
running application.

- `accessible-rdp.synthetic.v1` (the CSV schema these fixtures follow) is
  **not an official Shadowserver schema** — it is a locally controlled
  development contract, defined in
  `backend/src/services/ingestion/accessibleRdpRowValidator.js` and
  `backend/src/services/ingestion/accessibleRdpCsvParser.js`.
- Every IP address below is drawn from **RFC 5737 documentation ranges**
  (`203.0.113.0/24`, "TEST-NET-3") — never a real, routable, or organization
  address.
- Every timestamp is a **deterministic, explicit RFC 3339 UTC** value, chosen
  by hand to exercise a specific lifecycle transition (persistence,
  historical, closed-boundary, recurrence). Nothing here is randomly
  generated — the same files must produce the same result on every run.
- No real organization data, no real Shadowserver data, and no credentials
  or secrets appear anywhere in this directory.
- The expected results these fixtures should produce are recorded in
  `ground_truth.yaml`, **manually derived from the approved, documented
  lifecycle rules** in `STATUS.md` (P1-T4/P1-T5/P1-T6a) — never generated by
  running the program and copying its output back in as "expected."

**These fixtures must never be treated as operational threat intelligence,**
loaded into a production database, or presented as representing any real
network, organization, or incident.

## Layout

```
accessible-rdp/
  01_baseline.csv            — first upload: two distinct Finding identities,
                                one of them duplicated within the report
  02_persistence.csv         — a later observation for an existing OPEN
                                Finding, plus one brand-new Finding
  03_historical.csv          — an out-of-order earlier observation for an
                                existing OPEN Finding
  04_closed_boundary.csv     — an observation exactly at the closure boundary
                                of a Finding the evaluator has closed itself
                                (evaluation-only fixture setup, not a
                                production close endpoint — see
                                eval/lib/evalClosureFixture.js)
  05_recurrence.csv          — an observation after the closure boundary,
                                reopening the Finding
  06_mixed_validity.csv      — one valid row plus two invalid rows (bad IP,
                                out-of-range port)
  07_structural_rejection.csv — missing a required CSV header (protocol)

ground_truth.yaml            — manually authored expected results for every
                                scenario `eval/run_phase1_gate.js` runs
```

`01_baseline.csv` is also reused, byte-for-byte, for two further scenarios
that don't need their own fixture file: an identical re-upload (proving
file-level idempotency) and an untrusted-source rejection (proving source
validation runs before the bytes are ever parsed, so the same valid content
is rejected purely because of the `source` value passed to ingestion).

See `eval/run_phase1_gate.js` for how these fixtures and `ground_truth.yaml`
are used together to gate Phase 1.
