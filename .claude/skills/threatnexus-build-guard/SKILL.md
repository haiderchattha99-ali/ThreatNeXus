# ThreatNeXus Build Guard

ThreatNeXus is a CERT-focused CTI-to-response orchestration platform for PKCERT, built by a
four-person student team. A proposal has already been submitted. Every rule below backs a claim in
that PDF — breaking one makes a submitted document false, which is a worse failure than a missing
feature.

## Invariants — never violate

**AI is not in the decision path.**
- AI produces drafts and suggestions only. It never confirms incidents, closes cases, sends
  notifications, verifies remediation, changes risk scores, attributes activity to threat actors,
  claims compliance, or overrides an analyst.
- Every core workflow must complete with `AI_ENABLED=false`. That is the shipped default.
- Risk explanations are rendered from stored scoring factors, never generated by a model.
- Unreviewed AI output is excluded from every report and export — enforce at the query layer, not
  in a template.
- Approval is invalidated when an approved draft is edited or the underlying finding changes.

**Nothing leaves the system without recorded human approval.**
- The notification export endpoint must refuse any record whose status is not `Approved` or whose
  `approved_by` is null.
- Do not add an SMTP client, webhook sender, or ticketing integration — not even disabled. Its
  absence is the guarantee.

**Audit everything.** Every state change appends an `AuditLog` entry with actor, action, entity,
before/after, and TLP label. If you add a write path, you add its audit event in the same change.

**Remediation is a proxy, never a proof.** A finding disappearing from a later report sets a
remediation-proxy signal. Never a `remediated` boolean, never "verified closure". The asset may have
changed address, gone offline, or been missed by a scan.

**Persistence ≠ recurrence.** Dedup key is `(indicator_value, port, protocol, report_type)`.
- Existing finding, case open or absent → **persistence**: bump `occurrence_count`, update
  `last_seen`, recompute `days_unresolved`. No new finding row.
- Existing finding, linked case `Closed` → **recurrence**: bump `recurrence_count`, set the
  recurring flag, transition the case `Closed → Reopened`, audit it.

**One case holds one or more findings.** The `CaseFinding` join table is required. Never a single
`finding_id` foreign key on `Case`.

**Ownership confidence is not a risk factor.** Risk severity uses source severity, exposure/service
criticality, CVE presence, KEV status, EPSS, IOC reputation context, persistence, recurrence, days
unresolved, and sector criticality. Ownership confidence affects routing and actionability only.
Keep them in separate columns and separate explanations.

**Threat-intelligence reputation is supporting context, never proof.** A high AbuseIPDB abuse score
may raise prioritisation, cautiously and with a bounded weight. It must never independently confirm
an incident or set a finding to confirmed-compromised.

**Enrichment failure must never block ingestion.** If a provider times out, returns HTTP 429,
exhausts quota, rejects the key, or is unreachable, the finding is still created and the enrichment
row records `FAILED` or `RATE_LIMITED`. API keys come from environment variables only and are
redacted from every log line and error response. Automated tests use `MockProvider` and never consume
live quota.

**Framework mapping requires evidence.**
- An exposed service is a condition, not proof an attacker used it. No automatic ATT&CK mapping from
  exposure alone.
- Every mapping stores framework version, evidence reference, verbatim evidence quote, explanation,
  and two separate confidence values (`evidence_confidence`, `mapping_confidence`).
- Reject any framework ID absent from the pinned local catalogue.
- Reject any evidence quote that is not verbatim in the referenced source record.
- "No applicable mapping" is a valid, recordable outcome.
- ISO control **numbers and short titles only** — ISO text is copyrighted and must not be
  reproduced in the repository.

**Never add a "percentage of findings mapped" metric.** It creates pressure to force weak mappings.
Use "ownership resolution coverage" for the ownership metric, never "percentage mapped".

**TLP / sensitivity labels** on `RawReport`, `Finding`, `Case`, `Notification`, `FrameworkMapping`,
`AISuggestion`, `AuditLog`.

**Dashboards describe the loaded dataset only.** Label every view. Never present figures as national
cyber exposure statistics.

**The analyst dashboard is function-first.** Premium presentation is wanted, but: no animation may
delay investigation or approval · no critical action may be hidden behind a hover, drawer, or
transition · status is never communicated by colour alone · every chart answers a defined analyst
question · every metric traces to a real query over loaded data. The dashboard must remain fully
usable with all nonessential animation disabled and `prefers-reduced-motion` honoured. The cinematic
landing page is a **separate stretch surface** — it lazy-loads, degrades gracefully, and never blocks
access to the application or delays core workflow work.

## Anti-automation-bias rules (UI + API)

No pre-selected decision · no accept-all button · one suggestion reviewed at a time · evidence shown
beside the suggestion · rejection reason required · rejected suggestions retained for evaluation ·
suggestion cap per finding.

If a code change would make bulk-approving AI output easier, that is a defect, not a feature.

## AI output validation — all four gates, in order

1. Schema validation (express-validator / Zod). Failures are **discarded and logged, never silently
   repaired**.
2. Framework catalogue ID validation against the pinned catalogue.
3. Evidence-quote verbatim verification against the source record.
4. Suggestion cap per finding.

Prompts use fixed version-stamped templates, carry no organization names / exact IPs / contact
details (substitute real identifiers locally after generation), and wrap all ingested third-party
free text in a delimited untrusted-data block.

## Do not build

Live Shadowserver API · scheduled ingestion · automatic notification sending · automatic remediation
verification · SIEM or EDR integration · threat-actor attribution · automatic compliance assessment ·
SLA enforcement · organization portal · Redis/Celery · MISP/OpenCTI/TheHive/IntelMQ/n8n integration.

All are future scope. Adding one silently moves future scope into the MVP, which the proposal
explicitly promises not to do.

## Scope-cut order

Reduce report types, never workflow completeness. One complete workflow demonstrates the
contribution; several partial ones demonstrate nothing.

Cut in this order: second report type → dashboard breadth → AI notification drafting → AI entirely.

Never cut: audit logging, the analyst approval gate, evidence verification, the ground-truth dataset.

## Language to use in code comments, docs, and UI copy

| Use | Never |
|---|---|
| remediation proxy | verified remediation, verified closure |
| ownership resolution coverage | percentage mapped |
| loaded dataset | national statistics |
| exposure / finding | confirmed compromise, incident (unless evidence supports it) |
| suggestion, draft | decision, determination |
